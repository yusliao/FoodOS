## 1. 已确认的业务方向

- 系统购买者、拥有者和经营主体是一家运营方，一套部署服务该运营方及其合作饭店。
- 租户代表饭店客户，客户通过 Shop 向运营方订货并接受履约服务。
- admin 是运营方员工工作台，承接采购、库存、仓储、配送、客户及经营管理。
- dashboard 收敛为饭店客户门户，承接订货、订单、交付进度、售后与账号管理。
- 保留两个前端及现有模块化单体后端，不增加第三个前端，不拆微服务。
- 商品、供应商、采购、仓库、库存和履约作业属于运营方。客户不能因为成为租户管理员就获得内部经营权限。
- 订单、售后和交付保留一份权威业务记录；通过明确的客户归属与参与者权限支持双方操作，不复制两套单据。

本次用户确认优先于历史设计中“租户拥有完整供应链”“冲突时以脚手架为准”等不一致表述。保留源生成 Mediator、Contracts、EF Core、React、USD 默认币种以及当前语言配置等工程约束。

## 2. 当前问题与验收目标

当前源码把客户、门店、订单、仓库和库存放在相同的技术租户边界内；tenant 在业务能力上更接近独立运营企业。Basic 默认具有多个内部模块的查看权限；dashboard 路由主要只判断登录；Shop 缺少用户与门店的授权范围校验。

目标验收场景：饭店 A、B 以不同客户租户登录，同享运营方发布的可售商品，分别获取适用价格并下单；运营方统一采购、备货、配送；A、B 无法读取或修改彼此的订单、购物车、售后、价格和文件；员工按岗位操作，司机按任务归属操作。

检查结论来自静态源码，不能视为已验证当前 Docker 数据库或部署镜像。阶段 0 必须核对实施时的实际状态。

## 3. 实施原则与范围

- 顺序推进阶段 0—8，每个阶段先形成可验证的最小切片，再扩大范围。
- 每次先检查工作区及同类实现，保留其他任务修改，不自动提交、推送或新建分支。
- 使用现有模块；跨模块只能通过 Contracts。共享框架仅修改完成本次隔离目标所必需的部分，不做无关重构。
- 权限包含身份、动作权限、数据范围三部分。隐藏菜单、客户端 header、用户传入的 StoreId/TenantId 均不构成授权。
- 缺少身份或范围时默认拒绝；后台任务不得在缺少范围时自动当作超级管理员执行。
- 不在各 Handler 散布 IgnoreQueryFilters、任意切换租户或通用“跳过权限”开关。
- 不把所有业务实体标记为全局实体来绕过现有租户过滤。
- 保持库存账、幂等、并发、软删除、审计及状态机已有有效语义。
- 本次包含现有业务适配，不擅自扩展完整应收账款、税务、支付或新的结算模块。
- 生成迁移、检查脚本、测试方案属于实施准备；执行存量数据库迁移、批量回填、文件删除和生产发布仍按仓库规则取得对应明确授权。

## 4. 数据与身份设计基线

### 4.1 数据归属

- 运营方拥有：商品主档、供应商、采购、批次、库存流水、库位、仓储作业、车辆、线路和配送任务。
- 客户拥有访问范围：客户账号、授权门店、购物车、客户设置及客户侧文件。
- 交易记录明确标记客户租户及门店归属；运营侧读取需要员工身份和业务权限，客户侧读取必须限制客户租户及授权门店。
- 客户可见商品是运营商品的受控投影；不得返回成本价、供应商底价、内部备注、全仓库存明细等内部字段。
- 协议价由服务端根据已验证的客户关系解析，不能通过修改 CustomerOrgId 查询他人价格。
- 客户账号和运营员工仍复用 Identity，但两者身份及默认角色集合必须明确区分。

### 4.2 需要在阶段 0 固化的设计

- 现有技术 TenantId 的具体保留和迁移方式：区分身份租户与业务所有者，不能让同一字段在不同调用中暗中切换含义。
- 运营方单一实例的存储方式：不为了未来多运营方预建平台；也不把 root 超级管理员权限当普通员工权限。
- 饭店租户与 CustomerOrg、Store 的映射：默认面向单店客户，复用已有门店实体；未明确授权时客户只能访问绑定门店，不默认拥有同 tenant 下全部门店。
- 连锁多门店是否需要客户管理员分配成员权限。该决定只影响客户范围扩展，不阻止单店闭环实施。
- 既有“签收”是司机电子交付凭证还是客户收货确认；在明确规则前不改变完成订单的状态转换。
- 软件订阅 Billing 与采购货款结算分开；现有 Billing 不通过重命名充当交易账单。

设计取舍及源码依据直接记录在本文件的执行记录或链接的专题设计中。涉及实际数据归属的歧义必须单独列出，不能由脚本猜测。
