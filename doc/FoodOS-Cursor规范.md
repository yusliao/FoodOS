# FoodOS — Cursor 项目工作规范

> 使用说明：本文件是给 Cursor(及其他 AI 编程工具)看的项目上下文与行为规范，写代码前先读完。
> 落地建议：可以先整份放在仓库根目录 `AGENTS.md`，后续按第 9 节拆分成 `.cursor/rules/*.mdc` 多文件。
> 依据：本文基于《FoodOS-立项分析报告-V1.1》《FoodOS-子系统功能模块一览》《FoodOS-立项汇报提纲》整理，业务口径以这三份文档为准，本文件不重复业务背景，只提炼成可执行的代码规范。

---

## 1. 项目是什么（一句话）

FoodOS：面向餐饮客户的 **订货—仓配—溯源** 一体化操作系统。对标 Sysco，一个项目、一套部署、六个业务环节作为模块内聚，**不**按环节拆成多个独立系统。P0 目标：单城市、一类核心客户、一仓两至三温区的可演示闭环。

## 2. 硬性边界（写代码前必须知道）

**一期明确不做**（出现在需求里也不要顺手实现，提醒是路线图范围）：
- 全国仓网 / 自有车队相关的容量规划代码
- 自研收银 / 预订 / 叫号
- 区块链溯源
- **AI/预测模型直接写库存、自动生成采购单或自动派车** —— 只能出"建议"，必须经过人工确认节点才能落单据

**架构边界**：
- 一个代码仓库、一个数据库（分 schema）、模块化单体架构。**不要**建议或实现微服务拆分，除非用户明确要求。
- 不引入脚手架技术栈之外的新框架 / ORM / 状态管理库（第 7 节的温控占位是明确的例外）。

**范围边界（P0 只做这些）**：
订货 Shop、交易中枢（商品/价格/三维库存/订单状态机）、供应与质检、仓储 WMS、运输 TMS（基础版）、横切能力（权限/结算/看板基础）。计划引擎是 P1，客户经营是 P2 —— 没有被明确要求就不要提前实现。

## 3. 技术栈锁定

参照脚手架 [fullstackhero/dotnet-starter-kit](https://github.com/fullstackhero/dotnet-starter-kit)：

| 层 | 技术选型 |
|---|---|
| 运行时 | .NET 10 / C# latest |
| API | Minimal API + Mediator（源生成 CQRS）+ FluentValidation |
| ORM / DB | EF Core 10 / PostgreSQL，领域事件、Specification 模式、软删除+审计拦截器 |
| 权限 | JWT + ASP.NET Identity |
| 缓存 / 任务 | HybridCache on Valkey、Hangfire |
| 存储 | S3 / MinIO 预签名 |
| 前端 | React 19 + Vite 7 + TS、TanStack Query v5、React Router 7、Radix + Tailwind v4；locale JSON（不引入 i18next） |
| 本地化 | ASP.NET Core RequestLocalization；默认 `en-US`；P0：en-US / es-ES / fr-FR / de-DE / zh-CN |
| 货币 | 默认 **USD**（欧美试用） |
| 编排 | .NET Aspire（本地）、Docker Compose / Terraform（生产） |
| 测试 | xUnit、Testcontainers、NetArchTest（架构边界）、Playwright（前端 E2E） |

## 4. 模块边界（最重要，长期维护这一节）

| 模块 | 职责 | 优先级 | 备注 |
|---|---|---|---|
| `Ordering` | TOB 订货 Shop：组织账号、目录、合约价、购物车、下单截单、订单中心、售后 | P0 | |
| `Catalog` | 商品主数据、价格引擎（目录价/合约价/阶梯价/锁价） | P0 | |
| `Inventory` | 三维库存账（仓×温区×批次）、订单状态机 | P0 | 全链心脏，边界一旦定型不要轻易改 |
| `Procurement` | 供应商主数据、采购执行、收货质检、批次管理、追溯事件 | P0 | 采购下单与合格入库必须分权 |
| `Warehouse` | 库区库位、收货上架、波次计划、PDA 拣货、FEFO、复核装托、损耗登记 | P0 | |
| `Logistics` | 运力档案、固定线路、装车发运、司机端、在途跟踪、退货返仓 | P0 | 温控监测、异常判责、路径优化是 P1，先占位 |
| `Planning` | 需求预测、补货/调拨建议、计划员工作台 | P1 | 只设计接口/占位实体，不实现预测算法 |
| `CustomerOps` | 菜谱 BOM、用量建议、一键转购物车 | P2 | 不建 |
| `Identity` | 组织权限（复用 starter kit 自带） | P0 | |
| `Auditing` | 审计日志（复用 starter kit 自带） | P0 | |
| `Settlement` | 结算对账、发票账期 | 待定 | 归属未在详细设计中定案，见下方规则 |

**规则（AI 必须遵守）**：
1. 每个模块必须有 `.Contracts` 项目作为唯一对外接口。其他模块**只能**引用 Contracts，不能引用彼此的内部实现，不能直接查/改对方的 DbContext 或表。
2. 新建模块前先检查 `src/Modules/` 下是否已有可复用的模块结构，不要重复造轮子。
3. 任何跨模块调用，必须走 Contracts 定义的接口或领域事件——不能因为"图省事"临时打通两个模块的内部实现。
4. 像 `Settlement` 这种归属未定的模块，**不要自己拍板放进哪个模块**。用 `// TODO: 待业务负责人确认归属` 标注，并在回复里明确告知用户这是需要人工确认的点。

## 5. 领域规则（业务硬约束，代码必须体现）

- **三维库存**：仓库 × 温区 × 批次。任何库存变动必须落到批次级事件，不能只改汇总数字。
- **效期策略**：默认 FEFO（先效期先出），拣货和补货建议逻辑必须遵守。
- **订单状态机**：固定为 `草稿 → 预占 → 计划 → 拣货 → 在途 → 签收 → 对账`，不允许跳状态，每次状态变更必须发领域事件。
- **AI/预测只建议不执行**：任何会写入采购单、调拨单、派车单的代码路径，必须经过人工确认节点，预测/计划服务不能直接调用写入接口。
- **采购与质检分权**：收货质检和采购下单是两个不同角色、不同接口，不能揉在一起实现。
- **作业时钟可配置**：截单（16:00）、装车（22:00）、送达（05:00）、对账（10:00）等时间点是按仓/线路可配置的，不要写死具体时间常量。
- **默认货币 USD**：价盘、订单快照未指定币种时用 USD。不要改成 CNY。
- **多语言**：用户可见文案走资源或翻译表；API 读 `Accept-Language`；商品名等主数据按文化回退到 en-US。不要把单一语言写死在新功能里。

## 6. 开发工作流规范（给 Cursor 的行为指令）

- 写代码前先看对应模块的 `.Contracts` 项目有没有现成接口/DTO，不要凭空定义重复的类型。
- 新增或修改跨模块交互时，**先改 Contracts 层再实现**，PR/commit 里体现这个顺序。
- 遵循 Vertical Slice：一个 Command/Query 对应一个 feature 文件夹，不要拆成传统的 Controller/Service/Repository 散落多处。
- 每个新 Command/Query 都要配 FluentValidation validator + 单元测试。
- 涉及库存或订单状态机的改动，必须配 Testcontainers 集成测试，不能只写 Mock 单元测试。
- 模块间新增依赖时，同步新增/更新 NetArchTest 用例，让 CI 能拦住违规引用。
- 不确定的业务规则（结算模块归属、P1 功能细节、召回流程具体实现等）不要自己猜测实现——用 `TODO` 注释标记，并在回复里明确告知需要人工确认，不要静默假设。
- 涉及第 2 节"明确不做"清单里的功能，即使被随口提起，也要提醒这是一期不做的范围，不要顺手实现。

## 7. 明确允许的例外

- **温控 IoT 数据**：虽然完整实现是 P1，允许提前占位数据模型（如 `TemperatureReading` 实体、预留的事件类型），但不要实现完整的 MQTT broker 集成，除非被明确要求。

## 9. Cursor 落地格式建议

建议把本文件拆分成 `.cursor/rules/` 下多个 `.mdc` 文件，方便 Cursor 按需加载、也方便单独维护：

```
.cursor/rules/
├── 00-project-overview.mdc   # 对应第 1、2 节
├── 01-tech-stack.mdc         # 对应第 3 节
├── 02-module-boundaries.mdc  # 对应第 4 节 —— 最重要，随项目演进持续更新
├── 03-domain-rules.mdc       # 对应第 5 节
└── 04-workflow.mdc           # 对应第 6、7 节
```

在详细设计定案、模块边界确定后，第 4 节和第 5 节需要跟着更新——这两节是本文件里最容易过期、也最需要长期维护的部分。
