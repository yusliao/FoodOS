# 餐饮供应链操作系统（FoodOS）立项分析报告

版本：V1.0    日期：2026年9月8日    密级：内部资料
呈报对象：管理层 / 投资决策会
报告性质：立项分析（建议决策）
对标样本：Sysco（西斯科）；国内蜀海、美菜等实践
信息截止：公开资料截至 2026 年 9 月

================================================================================
一、请示事项（请决策）
================================================================================

建议本次会议明确以下三项：

1. 同意立项：建设「餐饮供应链操作系统」（暂定名 FoodOS），定位为 B 端餐饮食材与配套物资的订货—履约—溯源一体化平台，而不是资讯站或通用电商。

2. 同意建设方式：一个项目、一个代码仓库、一套生产部署。订货、库存、仓配、质检、运输、补货建议作为模块内聚，不按环节拆成多个独立系统。

3. 同意一期边界：先做单城市、一类核心客户、一仓两至三温区的可演示闭环（当天下午截单、夜间分拣、次日凌晨送达、批次可扫）。不在一期铺全国仓网、不自研完整收银 POS、不上区块链溯源。

如原则同意，建议授权启动 P0（8–12 周）详细设计与研发，并指定业务负责人与技术负责人各一名。

================================================================================
二、一页结论（供会上口头发言）
================================================================================

【我们要做成什么】
帮助餐饮客户（餐厅、团餐、连锁门店）在截单前完成订货，按冷藏/冷冻/常温准时履约，出问题能按批次召回，并在复购中提高粘性。对客户卖的是「稳定、准时、省心」，不是再做一个商城页面。

【为什么值得做】
全球标杆 Sysco 已证明：餐饮供应链的壁垒不在货架，而在「订货系统 + 仓配时钟 + 批次质量 + 帮客户算清补货」的一体化。2024–2026 年行业进一步把计划预测、温控责任、全托管/混履约做成可运营能力。国内万亿级餐饮背后的 B 端食材供应仍分散，区域型、可闭环的数字化供应链仍有窗口。

【为什么必须是一个项目】
这条链共用同一张订单号、同一个批次号、同一套库存账。拆成六个系统会出现「商城有单、仓库没单、财务对不上、召回找不到门店」。一个模块化单体：事故只停一处、对账只认一套账、运维只看四个指标——履约率、缺货率、损耗率、温控达标率。

【我们明确不抄的】
不抄 Sysco 的 300+ 物流中心和万级车队；不在没有密度时先建全国大仓（快驴类教训）；不把净利率约 2% 的重资产模式当成软件项目成功标准。软件成功标准是：单城先跑通、损耗和准时可量化、客户愿意复购。

【P0 结束时的成功画像】
试点城市目标客户能完成「下单 → 预占库存 → 夜拣 → 送达签收 → 扫码看批次」，且批次已贯穿出入库，具备模拟召回的数据基础。

三、背景与问题
================================================================================

3.1 调研起点
本报告源于对 FoodTalks 转载文章《Sysco：全球最大的供应链企业》（中渤经济 CNBO，2023-05-09）的拆解。该文描述 Sysco「田间到餐桌」模式：产品研发 + 销售中心（Sysco SHOP）+ 数字化供应链。文章是商业模式分析，不是软件规格。我们将其转化为可立项、可分期、可验收的产品与技术边界。

3.2 标杆事实（统一认知，非本期规模目标）
公开口径中，Sysco 服务数十万餐饮及相关客户，SKU 覆盖食材与非食配套。作业特征：截单后约 24 小时内履约、仓内分温区、自有冷链比例高、毛利率约 18%–19%、净利率约 2% 量级。扩张长期依赖并购与仓网密度，利润靠周转和规模，不是靠高毛利软件订阅。

可借鉴：作业时钟、一站式 SKU、采购与品控分权、订货与履约同一数据链、增值服务提高粘性。
不可作为一期 KPI：全国仓网、自有车队、世界 500 强体量。那是资本与时间换来的物理壁垒。

3.3 国内环境：有空间，不能照搬美国

维度          美国（Sysco 土壤）              中国（我们的约束）
下游          快餐连锁化率高、SKU 相对标准      正餐占比高、口味与 SKU 分散
上游          大型农场、集中度高               种养与流通仍偏分散，账期与垫资压力大
冷链标准化    基础设施成熟早                   温区、批次、损耗仍是利润漏点
已有玩家      Sysco / US Foods 等              蜀海（连锁全托管）、美菜（由重自营转向更轻连接）、区域配送商

结论：机会在「区域闭环 + 数字化履约 + 计划能力」，不在「先铺成全国 Sysco」。

================================================================================
四、行业最新态势（2024–2026）
================================================================================

2023 文给出骨架。近三年行业把骨架补成可运营的数字中枢，立项必须按新现实设计。

4.1 国际：订货平台变成经营入口，AI 进入生产降本
- Sysco Shop 从「再下一单」演进为含库存、配方成本、个性化推荐的客户工具；公开分析称活跃客户渗透高、线上订单规模达百亿美元量级。
- 技术上按域拆分 API（订货、商品、价格、配送、账户），核心交易引擎自研，外围用 CRM/CDP 等成熟件。
- 2026 财年业绩沟通中，Sysco 将库存预测、路径优化、后台自动化作为 AI 经营改造，并给出下一财年合计降本约 1 亿美元量级的指引（含此前措施结转）。智能体已走向销售、供应链、客户体验的生产使用。

对我们：AI 是模块内能力（预测建议、异常采购、路径），不是单独立项。一期数据和作业先跑准，模型只出建议，确认后才写采购单和派车单。

4.2 国内：计划运营与全托管成为差异化
- 蜀海加码自研数字化与 AI 计划，服务连锁「供给确定、成本确定、扩张确定」：集采、统仓统配、呆滞治理；品牌方保留选商定价，供应链方承接执行。
- 美菜等从全部自营配送转向更强调平台连接，反映纯重资产全国铺开难以持续。

对我们：系统必须预留自营仓配 + 供应商直送/共配的混合履约。

4.3 合规：溯源从宣传变成标准
- GB/T 45547-2025《食品生产追溯体系通用技术规范》已实施。
- T/CFCA 0003-2026《餐饮企业食品（食材）流通追溯评价要求》2026 年 5 月发布、6 月实施。
- GS1 EPCIS 2.0 支持将温湿度传感器事件写入追溯消息。

对我们：批次必须从收货贯穿到签收。一期用事件表 + 凭证存储，不上区块链。

五、项目定位
================================================================================

5.1 一句话
FoodOS：面向餐饮客户的订货—仓配—溯源操作系统。一个项目交付完整闭环；六个业务环节是模块，不是六个产品。

5.2 目标客户（建议收窄）
P0 主攻：区域连锁餐饮 / 团餐 / 中式快餐（有稳定周订单）——复购高、线路可沉淀。
P1：独立餐厅中的优质客户——服务成本高，后做。
暂缓：纯 C 端社区零售、全国多品牌一次性铺开。
非食配套（餐具、清洁、包材）可作为同仓常温 SKU，不作为一期主品类。

5.3 价值主张
对客户：下午四点前下单，次日开门前到货；缺货和临期可解释；出了事能追到批次。
对供应与品控：采购下单与合格入库分权，单供应商集中度可监控。
对我们：先用密度和周转活下来，再用补货建议提高客单价与留存。

5.4 明确不做（写入立项批复）
- 全国仓网与自有车队扩张不纳入本软件项目验收。
- 不自研完整餐厅收银、预订、叫号。
- 不以「40 万 SKU」为初期目标；试点以可履约核心品类为准。
- 不把资讯、会展、社群运营纳入本项目。

================================================================================
六、总体方案：一个项目，六个模块
================================================================================

6.1 建设原则
一个仓库：统一发布、统一版本、统一权限与客户主数据。
一张订单：从购物车到签收对账。
一个批次：从收货质检到门店，支撑召回。
模块边界：订货 / 中枢 / 供应质检 / 仓储 / 运输 / 客户经营，接口通信，禁止互相改表。
先闭环后智能：无稳定作业数据，不上自动派车、自动采购。

6.2 模块职责

模块          对应标杆        本期要解决的问题                      是否独立产品
订货 Shop     Sysco SHOP     合约价、截单、复购、可用量            否，入口
中枢          订单库存价格    防超卖、状态一致、三维库存            否，心脏
供应与质检    Source + QA    收货合格才入库、批次事件、供应商配额  否，合规
仓储 WMS      夜拣 FEFO      拣得到、拣得对、装得上                否，履约
运输 TMS      凌晨配 冷链    准时、温控、电子签收与退货            否，履约
客户经营      CAKE 轻量      用量建议、菜谱转购物车                否，P2 粘性

计划引擎（需求预测、补货/调拨建议）挂在中枢之上，只出建议，确认后才生成单据。

6.3 每日作业时钟（P0 验收剧本，可配置）
16:00 截单：之前可改单并预占；之后走加急或次日波次。
16:30–22:00 分拣：按温区拆波次，效期先进先出。
22:00–02:00 装车：托盘与车厢位扫码绑定。
05:00–08:00 送达：时间窗考核；无纸化签收；退货随车返回。
次日 10:00 前对账：签收差异、温控异常、退货进入同一订单。

6.4 技术路线（管理层压缩版）
形态：模块化单体（.NET / ASP.NET Core），按模块分项目、同一数据库分 schema，领域事件打通。
理由：团队与业务未到必须微服务的阶段；对标 Sysco 的域拆分用模块实现；待 IoT 或峰值成为瓶颈再按负载拆服务。
智能与物联网：温控 MQTT 写入运单；预测与路径作为模块内服务；大模型仅用于推荐与菜单草案，不自动下单。
溯源：关键追踪事件落库，凭证对象存储，对齐国标数据项。
详细设计在立项后两周内由技术负责人出具。

七、实施路径与资源
================================================================================

7.1 分期（一个项目内的交付线）

阶段            周期         范围                                      验收标准
P0 城市闭环     8–12 周      订货+中枢+一仓两/三温区+固定线路+质检批次   下午下单、凌晨送达、扫码见批次
P1 可控         再 8 周      供应商门户、召回、温控判责、计划员补货     模拟问题批次，数小时内列出位置
P2 粘性         再 8 周      菜谱补货、推荐、路径优化、部分直送         复购与渗透提升；混合履约可跑

P0 是本次立项唯一承诺；P1/P2 为路线图，按 P0 运营数据再批预算。

7.2 建议团队（P0）
业务负责人 1（可兼职）：客户规则、截单、温区、售后判责
产品 1：范围控制、验收剧本、主数据口径
技术负责人 + 后端 1+2：中枢、订单库存、仓配接口
前端/小程序 1：订货端、PDA、司机端（可分期）
测试 1：闭环场景与批次一致性
仓配顾问 兼职：库位、波次、装车现实约束

仓、车、人、货由业务侧并行准备，否则系统无法验收。

7.3 业务侧前置条件（书面确认）
1. 试点城市与试点仓（至少两温区物理条件）
2. 种子客户与核心品类清单（建议先几十个 SKU）
3. 截单时间、起订规则、配送时间窗
4. 供应商收货标准与不合格处理流程

7.4 投资口径（请财务测算后填数，本报告不虚构精确预算）
软件账：研发人力、云资源、短信/地图/对象存储、手持终端与基础温湿度探头。
运营账：仓租、车辆、货品铺货、销售团队——决定真实 ROI，必须与软件预算分闸，避免用系统预算扛仓配亏损。

八、效益与成功标准
================================================================================

8.1 不建议作为一期目标
对标 Sysco 全国市占、车队规模、40 万 SKU；「做成第二个 Sysco」的营收承诺。

8.2 建议写入立项的成功标准

P0：选定剧本 100% 可演示；真实订单开始统计履约成功率；库存必须按批次可核对；准点率与温控达标率开始有数；拣货差错与损耗有批次原因。

P1：召回演练通过（输入批次即可列出库存/在途/门店）；供应商集中度、收货合格率可监控。

商业结果（试点运营 3 个月后评估，不强制绑定 P0 软件验收）：周复购、客均 SKU、单仓人效、配送成本/件。

8.3 战略意义
本项目不是再做一个进销存，而是把交易、履约、合规、计划收口到一套操作系统。先区域跑通，再决定自营加深还是开放平台连接。选择权建立在账算得清的前提上。

十、一个项目 vs 多个项目（供质疑时使用）
================================================================================

对比项        一个项目（建议）              按环节多项目
客户体验      一次下单看到履约全程          多账号、状态对不齐
对账与召回    一个 ID 贯穿                  财务与食安对多套账
运维          一处发布、一个值班            联调成本随项目数上升
管理          一个负责人、一套 KPI          各项目优化局部、伤害全局
适用阶段      0 到 1、单城、小团队          已有稳定流量与独立扩缩之后

Sysco 级微服务是上百人、多国业务、多年并购系统的结果，不是起步形态。我们用模块对齐领域，用单体保证运维内聚。
