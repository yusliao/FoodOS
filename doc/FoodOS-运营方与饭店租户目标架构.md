# FoodOS 运营方与饭店租户目标架构

> 状态：已确认，作为《运营方与饭店租户改造实施清单》的阶段 0 实施基线。
> 日期：2026-09-15；2026-09-17 补充 WMS 权威边界。业务基线已确认，不代表外部接口与执行路径切换已经实现。

## 0. WMS 与 FoodOS 职责补充（2026-09-17，优先适用）

- 运营方已有 WMS，包含质检；没有配送/TMS。WMS 是实物库存及仓内执行唯一权威，负责收货、质检/隔离放行、库位、批次/FEFO、上架、波次派工、拣货复核、盘点和实际出库。
- FoodOS 保留交易与客户服务，管理采购、销售订单、售后、现有运营对账，并负责车辆、司机、路线、配送及签收；WMS 回传实际装车/出库，不能将其直接当成签收。
- FoodOS 库存数据是来源可追溯的业务可售视图/执行投影，不作为第二套实物库存权威。正式预占与释放由 WMS 确认；相关 API 能力待核实。断连仅允许浏览、购物车或待确认需求，不承诺库存和配送；交仓后改单取消须 WMS 确认，已出库走退货拒收。
- 当前仅实施外部 WMS 模式。保留现有自执行代码，对接仓库禁用相关前端入口、服务端命令及自动执行路径；只隐藏菜单不满足验收，不建设双执行模式。
- 下文运营方数据归属、root 身份和饭店隔离仍然有效，但数据归属不等于 FoodOS 对实物库存有独立写入权。第 3.2 节为既有自执行实现记录，不作为对接仓库派工方案；外部仓库的派工由 WMS 执行。
- 详见 [已确认 WMS 决策与待核实项](FoodOS-客户WMS对接-核心问题决策建议.md)。一期一个仓库，完整闭环及期初/在途对账、异常恢复验收后上线；文档确认不是迁移或部署授权。

## 1. 业务主体

FoodOS 是单一运营方购买并部署的订货、仓储和配送系统。运营方是商品、采购、库存、仓储和履约业务的所有者；饭店是运营方服务的客户。

- `root` 身份租户：运营方员工与系统恢复账号。
- 非 `root` 身份租户：饭店客户账号域。
- `admin`：运营方工作台，只接受 `root` 身份。
- `dashboard`：饭店客户门户，只接受非 `root` 身份。
- 一家饭店租户对应一个客户组织，P0 默认一个门店；模型允许以后增加多个门店。

技术租户用于身份、客户配置和客户访问边界。它不再表示一套独立的采购、库存、仓储和物流系统。

## 2. 数据归属

### 2.1 运营方共享数据

以下数据在单运营方部署内共享，不使用饭店 `TenantId` 作为所有权：

- Catalog：品牌、分类、商品、图片、价盘主档。
- Procurement：供应商、采购单、质检及采购追溯。
- Inventory：仓库、温区、批次、余额、预占、库存流水和日计划。
- Warehouse：库位、上架、波次、拣货、装托和损耗。
- Logistics：车辆、司机、线路、发运、站点、签收和随车退货。

这些实体是“单运营方共享实体”，不是无边界的公共数据。写入口只允许运营员工岗位；饭店只能通过专用客户查询获得经过裁剪的商品、价格、可售状态和交付投影。

### 2.2 客户及交易数据

Ordering 保留一份权威客户与交易记录：

- `CustomerOrg` 增加唯一的 `CustomerTenantId`。
- `Store` 通过 `CustomerOrgId` 归属客户，并增加稳定的客户租户查询索引。
- 新增用户门店授权关系，唯一键为客户租户、用户、门店。
- `Cart`、`SalesOrder`、`AfterSalesTicket` 显式保存 `CustomerTenantId` 和 `StoreId`。
- 订单行继续保存价格快照；不复制运营方订单和饭店订单。

客户请求先从登录身份取得 `CustomerTenantId`，再解析授权门店。请求中的租户、客户组织和门店标识只能缩小范围，不能扩大范围。

### 2.3 身份域数据

Identity 继续按技术租户隔离：

- `root` 中创建运营员工和岗位角色。
- 饭店租户中创建饭店管理员和普通成员。
- 饭店角色的权限目录不包含运营权限或 root 权限。
- 运营员工不能使用客户门户令牌；饭店用户不能使用运营工作台令牌。

### 身份查询与运营支持边界（2026-09-16）

- 已认证请求以签名令牌的身份域为准；`tenant` 请求头或查询参数与令牌冲突一律拒绝，root 也不能靠请求头切换客户。无请求头时仍从令牌建立身份域；匿名登录保留原租户选择方式。
- 用户列表、搜索、用户角色及角色详情限制在当前身份域；角色还须匹配 Operator/Customer 归属。历史错误归属角色不参与 JWT 或有效权限，客户角色的历史运营权限声明不进入有效权限或角色权限投影，不自动删除历史数据。
- 模拟登录是持有专门权限的 root 运营支持能力，保留授权记录和审计；客户不能启动、查询或撤销模拟登录授权。代登录使用目标客户权限，不能继承操作者权限或通过请求头返回 root；结束通过既有受控恢复流程。停用、超出宽限期或独立数据库客户不签发代登录令牌。
- 权限缓存增加身份域及版本标识，避免读取旧计算结果；发布须统一切换 API 实例。该调整不承诺多实例权限撤销瞬时一致性，也不批量清理旧缓存。
- 旧 admin 以 root 令牌携带客户请求头搜索用户的交互不再支持；阶段 5/6 须调整相关入口，不能恢复通用请求头身份切换。客户主题只读，修改/重置沿用现有运营权限目录。

## 3. 授权模型

### 工单协作补充（2026-09-16）

- 工单和评论是一份可由运营客服与报告人共同处理的记录，不复制运营副本。`CustomerTenantId` 是不可由请求体修改的来源客户身份域；`root` 值表示运营内部工单。
- 为保留历史数据，两个实体的 `CustomerTenantId` 映射现有物理 `TenantId` 列，不改写来源值。工单号继续在来源身份域内唯一，运营列表通过 `CustomerTenantId + Id` 区分不同客户的同号工单。
- TicketsDbContext 使用集中 `TicketAudience` 过滤：root 可进入运营工单范围，客户只能查询本身份域；客户 Handler 再检查报告人/受派人。软删除过滤独立保留，恢复工单只关闭软删除过滤，不关闭客户范围。
- 运营客服必须持有具体动作权限；指派/解决额外验证运营身份，处理人必须是 root 身份域中的有效用户。客户创建时不能指定处理人，但可以在自己的工单中回复、重开或关闭已解决工单。
- Files、Chat、Identity 和通知不随工单变为全局共享。工单私有附件通过 `ICrossTenantFileReadPolicy` 显式开放按文件 ID 的读取：文件须已完成上传、未软删除、来源为 root 或该工单客户，并校验当前用户的工单权限与参与范围。默认文件查询仍有租户过滤，不开放跨域列表、完成上传、修改、删除或恢复；普通文件和聊天文件不获得该例外。工单活动通知按下述参与者边界投递。
- 以目标单库共享 schema 部署为前提；历史租户若配置独立连接库，须先完成数据归并方案，不能用请求中切换数据库拼接客服视图。

每个请求同时满足三类条件：

1. 应用身份：运营员工或饭店客户。
2. 动作权限：查看、创建、质检、拣货、发运等。
3. 数据范围：客户租户、授权门店或分配任务。

`RequirePermission` 负责动作权限。业务 Handler 通过集中访问范围服务校验对象归属；不能相信前端隐藏、路由参数或 `X-FSH-App` header。

### 3.1 默认角色

- root 恢复管理员：平台及运营全部权限，只用于必要管理和恢复。
- 运营岗位：采购、质检、仓储主管、拣货、调度、司机、财务、客服等最小权限角色。
- 饭店管理员：本客户成员和门店授权管理、客户业务全部权限。
- 饭店成员：授权门店的商品、价格、购物车、订单、交付和售后权限。

饭店管理员不能创建、编辑或分配运营岗位。

### 3.2 波次派工（既有自执行实现，对接仓库不启用）

- 主管持有 `Warehouse.Waves.Assign`，通过 `/warehouse/waves/{waveId}/assign` 指派具有 Picks.View/Confirm 权限的活跃 root 员工；不以角色名称硬编码授权。
- 波次保存 AssignedPickerUserId；PickTask.PickerUserId 继续记录实际确认人。普通员工波次列表/详情按本人受派范围过滤；拥有派工权限且有 Waves.View 的主管可查看全部波次。mine 与确认无管理员代操作例外。
- 当前指派为一次性绑定，同人重试幂等、改派 409；并发指派保证单一胜者，不在本轮新增改派流程。
- 历史波次保持未指派，不自动回填。尚未拣货的波次由主管显式派工后进入个人任务；已有拣货记录或已完成的历史波次不可重写归属。发布须统一切换 API，避免旧实例继续暴露全量 mine；现有岗位需显式配置新的 Assign 权限，前端入口在阶段 5 接入。

### 3.3 运营通知与订阅导出

- 现有 `ops.*` 通知是运营内部摘要，仅允许 root 事件在 root 上下文处理；缺失、客户或不匹配的上下文拒绝写入与推送。
- 发运、签收和全仓待签收摘要要求 `Logistics.Shipments.View`，个人 `ViewAssigned`/POD 权限不能收到全量摘要；截单摘要同时要求 `Warehouse.Waves.View` 与 `Warehouse.Waves.Assign`。
- 运营收件箱写入与 SignalR 使用同一接收者筛选，保留活跃账号校验和既有通知去重。运营摘要的串行重放已验收；它的并发去重及持久化后推送失败的可靠性不由客户/工单通知测试证明。
- 不把内部通知复制到饭店租户。客户发运/签收通知先在 root 核对真实发运单、站点状态与订单归属，再通过既有事件总线进入客户身份域。Ordering Contracts 负责订单、组织、门店及有效用户门店授权的交集；通知消费时重查这些关系，并要求活跃账号具备 Shop.View 和 Notifications.Inbox.View。没有新端点或权限，不更改履约状态机。
- 业务表的规范化客户租户 ID 由 Multitenancy Contracts 解析回真实身份域 ID，不直接以大写业务值写入通知；大小写歧义、停用、超出宽限期、独立连接库及 root 均不作为客户投递目标。查询使用字面量转义，不把租户 ID 中的 `%` 或 `_` 当作通配符。
- 客户通知只含本订单 ID、门店 ID、活动类型及 `/shop/orders/{id}` 链接；不携带整车订单、仓库/路线/司机、其他门店或签收人/照片/坐标。收件箱按请求语言返回中英文标题，实时提示使用英文回退与稳定类型，前端展示接入仍在阶段 5/6。
- 客户投递事件按发运单、订单、活动和真实身份域生成稳定 ID，通知按该 ID 与用户去重；上游换事件 ID 重放也不会重复提醒。工单和客户通知共用幂等落库器，保留数据库主键并发冲突校验；运营摘要的既有实现未被替换。
- 既有发运/签收事件在业务保存后发布，仍有崩溃丢失窗口和推送失败窗口，不承诺必达或补发。重新检查授权只约束新投递；现有收件箱旧记录没有清理，也不回溯撤销已发送内容。未验证与撤权同时发生的竞态或权限缓存即时失效。
- 工单创建、指派、回复和状态变化通过 Tickets Contracts 发布活动，由既有事件总线在独立投递身份域作用域处理；事件显式区分来源、客户归属和投递身份域，不修改原请求 DbContext，不放开通知表租户过滤。该方式限于当前单库部署，不支持独立租户数据库协作。
- 投递时重查工单存在与客户归属，仅选报告人、当前受派人；创建时仍未分派且开放的工单可通知有 Assign 权限的运营队列。所有接收者还须为当前身份域活跃账号并具备 Tickets.View、Notifications.Inbox.View，排除操作者本人；改派后的旧处理人不再收到新活动。
- 工单通知仅保存活动类型、工单 ID/链接和通用标题，不复制标题、评论、客户资料。收件箱按当前语言返回中英文标题，实时提示使用默认英文和稳定类型；前端接入在阶段 5/6。通知 ID 按投递事件与用户确定，并发主键冲突仅在验证同一收件人记录存在后作为重放处理。
- 工单事件仍为保存后发布，没有 Outbox，失败可能丢失且不保证自动重试；SignalR 仅为落库后提示，不保证推送补发。幂等验收不等于可靠送达，也不回溯删除已发送的历史通知。
- 软件订阅发票 PDF 要求运营 Billing.View，饭店即使是历史发票所属租户也不能下载；这不是采购货款结算。后端未发现独立用户 CSV 导出端点，`Identity.Users.Export` 常量不表示已有导出实现。

### 3.4 SSE 传输边界

- 令牌仅由已认证且含有效用户/租户身份的请求签发，有效期 30 秒；连接身份来自令牌，不接受查询参数重指定用户或租户。令牌响应与流响应均为 `Cache-Control: no-store`。
- 有已注册 Redis/Valkey 连接时使用原子 GETDEL 消费，复用现有连接、不新增依赖；无 Redis 时仅提供单实例内存开发模式。Redis 异常直接失败，不降级到内存放行。
- 缓存键升级为 `sse:tok:v2:*`，与旧 IDistributedCache 的 hash 键隔离。滚动发布期间旧令牌不被新实例接受，客户端须重新换取令牌；应统一切换实例，不迁移仅 30 秒有效的临时令牌。
- 定向发送必须匹配 `TenantId + UserId`，移除无调用者的跨租户 BroadcastAll；同租户广播仅用于非敏感全员事件。业务发送者仍负责门店、岗位或资源参与者授权，不能用“同租户”替代业务数据范围。
- SSE 连接管理仍是单进程，无跨实例消息背板和离线补发；本次 Redis 双实例验证仅证明令牌单次消费，不等于跨实例推送能力。当前尚无业务发送调用，通知继续使用现有 SignalR。
- 持续流复用尚未完成的心跳/消息等待，断开时取消等待并清理连接。审计按服务端端点元数据识别 SSE，不缓存流响应；SignalR SSE 兼容检测仅用于 Hub 端点，普通 API 不能仅靠伪造 Accept 头跳过审计。
- 已建立连接不在每次心跳重新校验身份或业务权限；后续接入业务数据时须在发送路径校验当前接收范围，不能把持有连接当作永久业务授权。

## 4. API 边界

### 4.1 客户 API

客户门户使用 `/api/v1/shop/**`：

- `/catalog`、`/products/{id}`：客户可售投影。
- `/stores`：当前用户授权门店。
- `/stores/{storeId}/cart`：本门店购物车。
- `/orders`、`/orders/{id}`：本客户授权门店订单。
- `/after-sales`：本客户订单的售后。
- `/deliveries`：本门店交付状态裁剪投影。

客户 DTO 不包含供应商成本、全仓余额、其他客户标识、内部备注、路线内其他门店或内部审计负载。

### 4.2 运营 API

现有 Catalog、Procurement、Inventory、Warehouse、Logistics 及运营 Ordering API 由 admin 使用。运营查询可读取全部客户订单；岗位写操作继续使用模块权限和状态机。

旧 Ordering Shop 路由在兼容窗口内转调同一领域能力，不能长期保留两套业务实现。

### 4.3 现有订单对账边界（2026-09-16）

- 现有对账是同一销售订单的 `Received → Reconciled` 运营标记，不是新增货款结算。只有 root 身份域中持有 `Ordering.Orders.Reconcile` 的人员可调用既有 `POST /ordering/orders/{orderId}/reconcile`；未签收返回 409，已对账重复请求保持成功，不重复改动库存或价格。
- 运营订单列表 `/ordering/orders` 使用 `Orders.View`；客户列表 `/shop/orders` 使用 `Shop.View`。两端增加可选 `status=Received` 或 `status=Reconciled`（亦接受其他既有状态名称，大小写不敏感），在分页前过滤。省略状态保留原列表，非法状态返回 400；省略分页取第 1 页、20 条。
- 客户只能读取当前身份域、客户组织及当前有效授权门店的订单；授权记录须与门店当前归属一致。客户详情与列表使用相同范围，返回既有 ShopOrderDto：订购/交付/退回/短缺数量、单价、币种和运营对账状态，不开放运营内部字段或写入对账权限。
- 不生成重复订单、独立对账账本或“已付款”状态，不将订购金额/签收数量推导成未经确认的应收。已有售后规则仍允许对 Received/Reconciled 订单处理差异，因此 Reconciled 不表示财务冻结或双方确认。
- 新货款结算另行确认：模块归属、计价与退货扣减口径、账期、双方确认/异议流程、收款与核销、税费/发票、对账后的调整与审计留痕。本轮不实现这些能力，也不复用软件订阅账单。
- 页面筛选、运营对账按钮和运营提醒跳转在阶段 5/6 接入；本轮只完成后端双方访问适配，不宣称 UI 已迁移。

## 5. 持久化实现原则

- 运营共享实体和跨客户交易实体显式实现项目现有的全局实体标记，由各模块配置集中声明；这是业务所有权调整，不作为临时绕过查询过滤器的手段。
- 跨客户交易实体必须有 `CustomerTenantId`，所有客户查询从集中 Scope 生成谓词。
- 运营共享实体不预留多运营方 `OperatorId`；当前产品是一套部署服务一个运营方。
- 不通过请求期间切换 Finbuckle tenant 执行业务，不引入 service locator，不在 Handler 散布 `IgnoreQueryFilters()`。
- 数据库索引至少覆盖客户租户、门店和业务主键的常用组合；幂等键和单号在运营方共享范围内保持唯一。
- 跨模块只使用 Contracts，Ordering 不直接查询库存表，履约模块不直接修改订单表。

## 6. 迁移策略

迁移分为结构、回填、校验、切换和清理五步。生成迁移不代表执行数据库变更。

1. 新增客户归属和授权结构，先保持可空兼容。
2. 使用明确配置的运营数据来源回填运营共享数据；不能自动把第一个租户当运营方。
3. 建立租户与客户组织、门店映射，检查一对一冲突、孤儿订单和重复单号。
4. 双读校验数量、金额、库存余额和流水后切换应用。
5. 新代码稳定后再收紧非空约束并清理旧租户所有权字段和兼容路由。

演示数据使用 root 运营方、`acme`/`globex` 两个饭店租户。存量非演示数据库如果存在多个独立运营数据集，必须先指定合并来源和冲突处理规则，迁移不得猜测。

## 7. 当前页面迁移映射

- 迁入 admin：Catalog、客户与门店管理、运营订单、采购、WMS 质检/库存/仓储执行结果查询、同步异常与对账、FoodOS 配送、全量工单、审计、运营员工与岗位。外部仓库不迁入独立质检、库存调整、上架、波次派工、拣货执行按钮。
- 留在 dashboard：Shop 商品、购物车、本店订单、交付、售后、通知、个人安全及受限客户成员管理。
- 从 dashboard 移除：软件订阅、内部采购、仓储、物流管理、全租户审计、运营角色编辑。
- root 租户管理和系统恢复入口留在 admin，并与日常岗位导航分开。
- 5.1 已落地运营工作台入口：admin 固定 root 身份域，恢复/刷新/跨标签页同步统一检查运营身份，启动重新获取岗位权限，失败关闭受限入口。首页与桌面/移动导航共用权限规则；系统管理和软件订阅独立分区，首页不加载订阅统计，KPI 按 Ops.Kpis.View 加载。当前仅展示已存在的授权页面，业务迁入及员工岗位编辑完整适配继续按 5.2—5.5 执行。前端门禁不替代后端签名与对象归属验证。

5.2 进度：合作客户/门店查询及新建已在 admin 接入现有 Ordering API，商品及定价尚待迁移。合作档案与技术身份域分离：新建档案不创建登录域，不授予用户门店访问权；身份域由系统管理员提供，当前后端未联动验证其存在性。门店从关联非 root 身份域的客户建立，继承客户归属并选择运营仓库。现有无修改/删除接口，不新增空操作；默认线路配置和成员授权不在此新建流程内。

## 8. 明确不在本轮扩展

- 第三套前端、微服务拆分、多运营方 SaaS。
- 完整应收、支付、税务和新 Settlement 模块。
- 改写现有签收状态含义；客户收货确认是否独立于司机 POD 后续单独决定。
- 连锁饭店的复杂组织层级。当前通过用户门店授权关系支持以后扩展。
