# FoodOS 运营方与饭店租户目标架构

> 状态：已确认，作为《运营方与饭店租户改造实施清单》的阶段 0 实施基线。
> 日期：2026-09-15。

## 1. 业务主体

FoodOS 是单一运营方购买并部署的订货、仓储和配送系统。运营方是商品、采购、库存、仓储和履约业务的所有者；饭店是运营方服务的客户。

- `root` 身份租户：运营方员工与系统恢复账号。
- 非 `root` 身份租户：饭店客户账号域。
- `admin`：运营方工作台，只接受 `root` 身份。
- `dashboard`：饭店客户门户，只接受非 `root` 身份。
- 一家饭店租户对应一个客户组织，P0 默认一个门店；模型允许以后增加多个门店。

技术租户用于身份、客户配置和客户访问边界。它不再表示一套独立的采购、库存、仓储和物流系统。

## 2. 数据归属

### 2.1 运营方共享数据

以下数据在单运营方部署内共享，不使用饭店 `TenantId` 作为所有权：

- Catalog：品牌、分类、商品、图片、价盘主档。
- Procurement：供应商、采购单、质检及采购追溯。
- Inventory：仓库、温区、批次、余额、预占、库存流水和日计划。
- Warehouse：库位、上架、波次、拣货、装托和损耗。
- Logistics：车辆、司机、线路、发运、站点、签收和随车退货。

这些实体是“单运营方共享实体”，不是无边界的公共数据。写入口只允许运营员工岗位；饭店只能通过专用客户查询获得经过裁剪的商品、价格、可售状态和交付投影。

### 2.2 客户及交易数据

Ordering 保留一份权威客户与交易记录：

- `CustomerOrg` 增加唯一的 `CustomerTenantId`。
- `Store` 通过 `CustomerOrgId` 归属客户，并增加稳定的客户租户查询索引。
- 新增用户门店授权关系，唯一键为客户租户、用户、门店。
- `Cart`、`SalesOrder`、`AfterSalesTicket` 显式保存 `CustomerTenantId` 和 `StoreId`。
- 订单行继续保存价格快照；不复制运营方订单和饭店订单。

客户请求先从登录身份取得 `CustomerTenantId`，再解析授权门店。请求中的租户、客户组织和门店标识只能缩小范围，不能扩大范围。

### 2.3 身份域数据

Identity 继续按技术租户隔离：

- `root` 中创建运营员工和岗位角色。
- 饭店租户中创建饭店管理员和普通成员。
- 饭店角色的权限目录不包含运营权限或 root 权限。
- 运营员工不能使用客户门户令牌；饭店用户不能使用运营工作台令牌。

## 3. 授权模型

### 工单协作补充（2026-09-16）

- 工单和评论是一份可由运营客服与报告人共同处理的记录，不复制运营副本。`CustomerTenantId` 是不可由请求体修改的来源客户身份域；`root` 值表示运营内部工单。
- 为保留历史数据，两个实体的 `CustomerTenantId` 映射现有物理 `TenantId` 列，不改写来源值。工单号继续在来源身份域内唯一，运营列表通过 `CustomerTenantId + Id` 区分不同客户的同号工单。
- TicketsDbContext 使用集中 `TicketAudience` 过滤：root 可进入运营工单范围，客户只能查询本身份域；客户 Handler 再检查报告人/受派人。软删除过滤独立保留，恢复工单只关闭软删除过滤，不关闭客户范围。
- 运营客服必须持有具体动作权限；指派/解决额外验证运营身份，处理人必须是 root 身份域中的有效用户。客户创建时不能指定处理人，但可以在自己的工单中回复、重开或关闭已解决工单。
- Files、Chat、Identity 和通知不随工单变为全局共享。工单私有附件通过 `ICrossTenantFileReadPolicy` 显式开放按文件 ID 的读取：文件须已完成上传、未软删除、来源为 root 或该工单客户，并校验当前用户的工单权限与参与范围。默认文件查询仍有租户过滤，不开放跨域列表、完成上传、修改、删除或恢复；普通文件和聊天文件不获得该例外。工单活动通知仍需单独实现与验收。
- 以目标单库共享 schema 部署为前提；历史租户若配置独立连接库，须先完成数据归并方案，不能用请求中切换数据库拼接客服视图。

每个请求同时满足三类条件：

1. 应用身份：运营员工或饭店客户。
2. 动作权限：查看、创建、质检、拣货、发运等。
3. 数据范围：客户租户、授权门店或分配任务。

`RequirePermission` 负责动作权限。业务 Handler 通过集中访问范围服务校验对象归属；不能相信前端隐藏、路由参数或 `X-FSH-App` header。

### 3.1 默认角色

- root 恢复管理员：平台及运营全部权限，只用于必要管理和恢复。
- 运营岗位：采购、质检、仓储主管、拣货、调度、司机、财务、客服等最小权限角色。
- 饭店管理员：本客户成员和门店授权管理、客户业务全部权限。
- 饭店成员：授权门店的商品、价格、购物车、订单、交付和售后权限。

饭店管理员不能创建、编辑或分配运营岗位。

### 3.2 波次派工

- 主管持有 `Warehouse.Waves.Assign`，通过 `/warehouse/waves/{waveId}/assign` 指派具有 Picks.View/Confirm 权限的活跃 root 员工；不以角色名称硬编码授权。
- 波次保存 AssignedPickerUserId；PickTask.PickerUserId 继续记录实际确认人。普通员工波次列表/详情按本人受派范围过滤；拥有派工权限且有 Waves.View 的主管可查看全部波次。mine 与确认无管理员代操作例外。
- 当前指派为一次性绑定，同人重试幂等、改派 409；并发指派保证单一胜者，不在本轮新增改派流程。
- 历史波次保持未指派，不自动回填。尚未拣货的波次由主管显式派工后进入个人任务；已有拣货记录或已完成的历史波次不可重写归属。发布须统一切换 API，避免旧实例继续暴露全量 mine；现有岗位需显式配置新的 Assign 权限，前端入口在阶段 5 接入。

### 3.3 运营通知与订阅导出

- 现有 `ops.*` 通知是运营内部摘要，仅允许 root 事件在 root 上下文处理；缺失、客户或不匹配的上下文拒绝写入与推送。
- 发运、签收和全仓待签收摘要要求 `Logistics.Shipments.View`，个人 `ViewAssigned`/POD 权限不能收到全量摘要；截单摘要同时要求 `Warehouse.Waves.View` 与 `Warehouse.Waves.Assign`。
- 收件箱写入与 SignalR 使用同一接收者筛选，保留活跃账号校验和既有通知去重。串行重放已验收；并发去重及持久化后推送失败的可靠性不由本次测试证明。
- 不把内部通知复制到饭店租户。客户配送通知需另按客户与授权门店生成受控载荷；工单通知需按参与者生成，均仍待实现。现有收件箱旧记录没有清理，也没有回溯撤销已发送内容。
- 软件订阅发票 PDF 要求运营 Billing.View，饭店即使是历史发票所属租户也不能下载；这不是采购货款结算。后端未发现独立用户 CSV 导出端点，`Identity.Users.Export` 常量不表示已有导出实现。

## 4. API 边界

### 4.1 客户 API

客户门户使用 `/api/v1/shop/**`：

- `/catalog`、`/products/{id}`：客户可售投影。
- `/stores`：当前用户授权门店。
- `/stores/{storeId}/cart`：本门店购物车。
- `/orders`、`/orders/{id}`：本客户授权门店订单。
- `/after-sales`：本客户订单的售后。
- `/deliveries`：本门店交付状态裁剪投影。

客户 DTO 不包含供应商成本、全仓余额、其他客户标识、内部备注、路线内其他门店或内部审计负载。

### 4.2 运营 API

现有 Catalog、Procurement、Inventory、Warehouse、Logistics 及运营 Ordering API 由 admin 使用。运营查询可读取全部客户订单；岗位写操作继续使用模块权限和状态机。

旧 Ordering Shop 路由在兼容窗口内转调同一领域能力，不能长期保留两套业务实现。

## 5. 持久化实现原则

- 运营共享实体和跨客户交易实体显式实现项目现有的全局实体标记，由各模块配置集中声明；这是业务所有权调整，不作为临时绕过查询过滤器的手段。
- 跨客户交易实体必须有 `CustomerTenantId`，所有客户查询从集中 Scope 生成谓词。
- 运营共享实体不预留多运营方 `OperatorId`；当前产品是一套部署服务一个运营方。
- 不通过请求期间切换 Finbuckle tenant 执行业务，不引入 service locator，不在 Handler 散布 `IgnoreQueryFilters()`。
- 数据库索引至少覆盖客户租户、门店和业务主键的常用组合；幂等键和单号在运营方共享范围内保持唯一。
- 跨模块只使用 Contracts，Ordering 不直接查询库存表，履约模块不直接修改订单表。

## 6. 迁移策略

迁移分为结构、回填、校验、切换和清理五步。生成迁移不代表执行数据库变更。

1. 新增客户归属和授权结构，先保持可空兼容。
2. 使用明确配置的运营数据来源回填运营共享数据；不能自动把第一个租户当运营方。
3. 建立租户与客户组织、门店映射，检查一对一冲突、孤儿订单和重复单号。
4. 双读校验数量、金额、库存余额和流水后切换应用。
5. 新代码稳定后再收紧非空约束并清理旧租户所有权字段和兼容路由。

演示数据使用 root 运营方、`acme`/`globex` 两个饭店租户。存量非演示数据库如果存在多个独立运营数据集，必须先指定合并来源和冲突处理规则，迁移不得猜测。

## 7. 当前页面迁移映射

- 迁入 admin：Catalog、客户与门店管理、运营订单、采购、质检、库存、上架、波次、拣货、配送、全量工单、审计、运营员工与岗位。
- 留在 dashboard：Shop 商品、购物车、本店订单、交付、售后、通知、个人安全及受限客户成员管理。
- 从 dashboard 移除：软件订阅、内部采购、仓储、物流管理、全租户审计、运营角色编辑。
- root 租户管理和系统恢复入口留在 admin，并与日常岗位导航分开。

## 8. 明确不在本轮扩展

- 第三套前端、微服务拆分、多运营方 SaaS。
- 完整应收、支付、税务和新 Settlement 模块。
- 改写现有签收状态含义；客户收货确认是否独立于司机 POD 后续单独决定。
- 连锁饭店的复杂组织层级。当前通过用户门店授权关系支持以后扩展。
