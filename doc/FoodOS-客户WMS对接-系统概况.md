# FoodOS 与客户现有 WMS 对接：系统概况

> 2026-09-17 更新：用户已确认 WMS 为实物库存及仓内执行权威，包含质检；客户没有 TMS，由 FoodOS 承担配送和签收。以下“当前模型”描述既有自执行源码，不是外部仓库的目标职责；对接及切换尚未实现。详见 [已确认决策](FoodOS-客户WMS对接-核心问题决策建议.md)。

> 文档用途：提供给客户仓库系统开发人员，帮助其快速理解 FoodOS 的业务定位、仓配模型和双方系统边界。
>
> 状态：沟通稿。本文描述当前 FoodOS 的实际实现与已确认目标；具体接口字段、状态映射和时效要求需双方评审后冻结。

## 1. 项目背景

FoodOS 是运营方使用的餐饮订货、采购、库存、仓储、配送与追溯系统。饭店通过 FoodOS 的 Shop 门户下单，运营方统一管理商品、库存及履约。

客户目前已经有一套运行中的仓库系统（下称“客户 WMS”）。本次对接不要求立刻替换客户 WMS，而是让 FoodOS 与客户 WMS 协同：

- FoodOS 管客户订单、商品销售、价格、采购、可售库存视图、履约进度以及车辆/司机/路线/配送签收。
- 客户 WMS 管实物库存、正式预占/释放、收货质检与放行、库位/批次、FEFO、上架、组波派工、拣货复核、盘点和实际出库。
- 双方通过受控接口同步任务和执行事实，不直接访问或修改对方数据库。

特别说明：客户 WMS 代表运营方已有的仓储执行能力，不是 FoodOS 中的饭店租户。饭店用户只能看到自己的订单和交付投影，不能访问仓库内部数据。

## 2. FoodOS 技术形态

FoodOS 当前是 .NET 10 模块化单体，使用 PostgreSQL、EF Core、Minimal API、源生成 Mediator、Outbox/Inbox、后台任务和集成事件。核心模块之间通过 Contracts 调用或事件协作，不直接修改其他模块的数据表。

与仓储对接相关的模块包括：

- `Catalog`：商品、SKU、温区属性和价格基础数据。
- `Ordering`：饭店、门店、购物车、销售订单、订单行和售后。
- `Inventory`：仓库、温区、批次、库存余额、预占和库存流水。
- `Procurement`：供应商、采购订单、收货预约和质检。
- `Warehouse`：库位、上架、波次、拣货任务、装托和损耗。
- `Logistics`：路线、车辆、司机、发运单、站点、签收和返仓。
- `Ops`：跨模块的批次追溯和经营指标聚合。

## 3. 当前业务链路

本节及第 4—5 节是既有自执行实现说明。目标链路为 FoodOS 接收需求 → WMS 确认预占 → FoodOS 下发履约要求 → WMS 分配/组波/拣货/装车出库 → FoodOS 配送签收；对接仓库不得同时运行下图中的本地预占、波次及 FEFO 执行。WMS 接口能力尚待核实。

```mermaid
flowchart LR
    A[饭店 Shop 下单] --> B[Ordering 创建销售订单]
    B --> C[Inventory 预占库存]
    C --> D[截单与日计划]
    D --> E[Warehouse 生成波次]
    E --> F[Inventory 按 FEFO 分配批次]
    F --> G[仓库拣货与装托]
    G --> H[Logistics 装车发运]
    H --> I[门店签收/POD]
    I --> J[订单收货与对账]
```

销售订单状态主链为：

```text
Draft → Reserved → Planned → Picking → Packed → InTransit → Received → Reconciled
```

取消和改单主要发生在截单前。状态不能由外部系统任意跳转，必须由 FoodOS 业务规则检查前置状态后推进。

## 4. FoodOS 库存模型

FoodOS 的库存不是单一 SKU 数量，而是“仓库 × 温区 × 批次 × 商品”的库存账。

批次余额包含：

- `OnHand`：在库数量。
- `Reserved`：已接单、尚未分配具体批次的数量。
- `Allocated`：波次已经分配到批次的数量。
- `Picked`：已拣、未发运数量。
- `InTransit`：运输中数量。
- `Isolated`：质检、临期或异常隔离数量。

当前可用库存按在库量扣除预占、已分配和隔离数量计算，并结合批次状态和效期判断。

重要规则：

1. 下单时按仓库、温区、SKU 做预占，不立即锁定具体批次。
2. 波次启动时才按 FEFO 分配具体批次。
3. 每次库存变化必须写库存流水。
4. 重复请求必须使用稳定幂等键，不能重复增减库存。
5. 外部库存快照不能直接覆盖 FoodOS 的库存余额。

## 5. 当前仓储模型

FoodOS Warehouse 当前包含：

- `Location`：仓库、温区、库位编码和库位类型。
- `PutawayTask`：合格入库后的上架任务。
- `DailyPlan`：按仓库和业务日形成的作业计划。
- `Wave`：按业务日、温区和线路组织的出库波次。
- `PickTask`：订单行对应的批次、库位、数量和拣货状态。
- `PackTote`：订单和周转箱/托盘的装载关系。
- `Shrinkage`：按批次记录的损耗。

当前 `PickTask` 使用 FoodOS 内部 GUID 关联订单、订单行、商品、批次、库位和预占。客户 WMS 的任务编号、波次编号和库位编号不能直接替代这些内部 ID，需要建立明确的外部 ID 映射。

## 6. 采购与入库规则

采购由 FoodOS 管理，收货质检及最终放行由 WMS 管理：

- 采购订单下发后进入收货阶段。
- 仓库实际收货数量属于现场事实。
- 质检合格数量才能进入可用库存。
- 不合格数量进入隔离或拒收流程，不能自动变成可售库存。
- 质检岗位和采购岗位分权。

因此，客户 WMS 回传“已收货”不等于可售，须取得 WMS 放行结果。FoodOS 展示质检事实，不通过原本地质检接口再次入库或创建上架任务；结果映射、更正及证据接口仍待核实。

## 7. 发运与签收规则

FoodOS Logistics 管理：

- 路线、车辆和司机。
- 发运单、门店站点和订单装载关系。
- WMS 回传的实际批次和装车数量（不独立决定仓内批次）。
- 门店签收、照片、签收人、地理位置和退货。

库存状态会随履约推进：

```text
Allocated → Picked → InTransit → Delivered
```

退货或拒收由 FoodOS 记录交付异常，WMS 确认实际返仓、复检、隔离/放行及上架；FoodOS 不凭司机登记直接增加可售库存。上方库存状态是现有内部模型，外部库存同步不得机械重放本地自执行动作。

## 8. FoodOS 希望从客户 WMS 获得的现场事实

初步需要的事实包括：

- 仓库、温区、库位和作业能力。
- 商品/SKU 与包装单位。
- 批次、生产日期、效期和产地。
- 收货数量、收货时间和收货差异。
- 上架库位和上架数量。
- 履约需求接收结果、WMS 波次及任务进度。
- 实际拣货批次、数量、短配和替代情况。
- 复核、装箱、托盘或 SSCC 信息。
- 装车和出库时间。
- 盘点结果、损耗和异常冻结。
- 返仓和退货结果。

## 9. FoodOS 计划向客户 WMS 提供的数据

初步包括：

- 商品和 SKU 基础信息。
- 采购订单和入库预约。
- 销售订单或标准化出库任务。
- 门店、地址和交付时窗。
- 温区、数量、单位和效期要求。
- 交付约束与配送装载要求，不下发另一套独立波次或拣货派工。
- 订单取消、改单和任务撤销。
- FoodOS 内部关联号、业务日期和幂等键。

WMS 负责波次、批次及仓库执行单；FoodOS 负责配送任务。双方仍须明确拆单/合单映射及预约接口，不要求单据一对一。

## 10. 对接基本原则

- 双方不直连数据库。
- 每个外部对象都要有稳定外部 ID。
- 采用至少一次投递，消费方必须幂等。
- 原始报文应可审计、可重放。
- 外部状态必须映射为 FoodOS 标准状态，未知状态不能自动猜测。
- 库存差异先对账、再人工确认，不能自动覆盖。
- 测试环境和生产环境使用独立连接和凭证。
- 饭店客户隔离不能因 WMS 对接被绕过。

## 11. 已确认边界与仍需技术核实的问题

库存、质检、批次/FEFO、波次派工及仓内执行归 WMS；配送与签收归 FoodOS。WMS 正式预占确认前不承诺供货，断连允许待确认需求但不承诺配送，交仓后改单取消必须获得 WMS 确认。

仍需核实：预占/释放/查询接口、可售库存口径、预约/月台接口、事件推送或增量查询、稳定 ID/版本/游标、商品/单位/货主映射、部分执行与取消状态，以及期初快照和未完成单据对账。首期一个仓库，具体仓库和测试样本待选；完整闭环验收前不开放正式交易。
