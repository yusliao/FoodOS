# FoodOS 客户 WMS 对接：核心问题决策建议

日期：2026-09-16；2026-09-24 更新。

状态：用户已确认下列业务责任和一期方向；接口能力、字段、状态映射及联合验收仍待 WMS 团队核实。业务确认不代表代码已实现或允许执行数据库迁移、生产切换。

## 已确认决策（2026-09-24 最新实施依据）

用户确认：运营方现有 WMS 为权威且包含质检；客户没有配送/TMS 系统；其余按本次推荐执行。

1. WMS 是实物库存和仓内执行的唯一权威：收货、质检、隔离放行、库位、批次与 FEFO、上架、波次、派工、拣货、复核、盘点调整及实际出库由 WMS 负责。FoodOS 不建立第二套独立仓内决策。
2. FoodOS 负责客户、销售商品与价格、采购及销售订单、售后与现有运营对账；同时负责车辆、司机、路线、配送任务和签收。FoodOS 提供装载要求，WMS 回传实际装车/出库；出库、发车、签收不得混同。
3. WMS 负责实物库存及仓内是否实际占用；FoodOS 保存用于展示的可售库存视图，但饭店下单先形成 FoodOS 平台承诺，不同步等待 WMS 正式预占，也不回退为 FoodOS 独立实物扣减。
4. WMS 断连时 FoodOS 仍允许下单、改单和取消，可靠异步发送出库或取消通知。交易状态与仓库确认状态分离；连接失败保持待确认，明确拒绝或短配进入仓库异常。
5. 交仓前遵循 FoodOS 截单规则；改单/取消先由 FoodOS 受理再异步通知 WMS。WMS 已拣货或已出库时，根据回传进入异常、退货或拒收，不把 FoodOS 已受理误表示为仓内已执行。
6. 当前项目只实施外部 WMS 执行模式。已有 FoodOS 自执行代码及未提交工作保留，但对接仓库必须禁用相关入口和服务端执行路径；不为未来场景建设双执行模式，不以隐藏按钮代替后端防线。
7. 一期一个仓库，先跑通采购收货/质检、可售库存与预占、出库回传、FoodOS 配送签收、取消和异常恢复。完成期初库存、未完成单据对账与联合验收后再开放正式交易。
8. admin 仓储相关页面转为结果查询、进度、异常重试和对账，不迁入另一套质检、库存调整、上架、波次或拣货执行工作台。

以上决策优先于其他文档及下文历史建议中相冲突的职责表述。下文“双方需确认”主要用于落实接口、数量口径和异常流程，不再将上述责任方作为未决选项。到货预约/月台接口、商品主档交换、库存口径、单位/货主映射、事件机制、具体试点仓库与验收阈值仍需联合评审；不得擅自补全。

## 一、目的与适用前提

本文针对沟通清单中第 12—21 项核心问题，逐条提出建议、理由和需要双方确认的边界。编号保持原清单编号，第 11 项为“当前仍需双方确认的核心问题”标题。

本文假设“客户 WMS”指购买 FoodOS 的运营方已有的 WMS，而不是饭店租户自己的 WMS。

- 运营方是 FoodOS 的系统拥有者和购买者。
- 饭店租户是运营方服务的采购客户，通过 FoodOS 下单、查看配送和处理售后。
- 如果实际对接的是饭店自己的 WMS，应另行确认边界：通常同步采购、配送和收货，不由其控制运营方仓库的波次和拣货。

总原则：FoodOS 管交易和客户服务，WMS 管仓内实物执行。同一个业务决定只能有一个系统负责，不能让双方同时分配库存、创建拣货任务，再依靠同步消除冲突。

以下保留各项决策理由与落地核查问题，责任方按顶部已确认决策执行；不代表当前代码已经实现，也不替代对客户 WMS 实际能力的调查。

## 12. 客户 WMS 是仓内执行系统，还是库存权威系统？

### 建议

成熟 WMS 作为实物库存权威，FoodOS 保存业务可售库存视图。

- WMS：实际库存、库位、批次、冻结、残次、盘点调整及仓内占用。
- FoodOS：订货规则、客户限购、订单需求，以及用于展示和接单的可售库存视图。
- FoodOS 下单形成平台承诺并异步下发履约需求；WMS 决定实际占用和分配，FoodOS 不再扣一次实物库存。

### 理由

实物变化发生在仓库，WMS 最接近事实。两边各自维护一套最终库存，会导致库存差异难以归责和修复。

WMS 库存数量不一定直接等于可售数量。质检冻结、其他渠道占用、安全库存等因素必须纳入统一口径。

### 双方需确认

- 库存各状态的定义、可售计算公式和同步时效。
- 暂占、正式分配、取消释放及超时释放在 WMS 内的具体状态映射。
- WMS 短配、拒绝和长期未确认时的运营处置时限与客户沟通规则。

## 13. 哪个系统创建波次和拣货任务？

### 建议

对接仓库由 WMS 创建波次和拣货任务，FoodOS 下发履约需求并接收执行进度。

FoodOS 提供订单、商品、数量、交付时限和配送要求；WMS 决定组波、任务拆分、人员分配和短拣处理。

“主管按波次派给拣货员，员工只查看和确认本人任务”的规则，在 WMS 接管的仓库由 WMS 执行。FoodOS 可以展示结果，不再生成一套独立任务。

### 理由

波次与拣货依赖库位、人员和实时仓内状态，由 WMS 统一决策更完整，也能避免重复作业。

### 双方需确认

- 组波、派工、短拣、取消及重新分配规则。
- FoodOS 展示到波次、任务还是订单进度层级。
- 当前试点仅采用外部 WMS 执行；核实如何阻断已有 FoodOS 自执行入口及后台路径。

## 14. 哪个系统决定批次分配和 FEFO？

### 建议

FoodOS 提供交付约束，WMS 负责实际批次选择与 FEFO（先到期先出）执行。

例如：FoodOS 指定客户要求到货时剩余保质期至少 7 天；WMS 从满足质检、冻结、效期和库存条件的批次中分配，并回传实际发出批次及数量。

### 理由

FEFO 不只是到期日期排序，还受到实物可用状态和仓内条件限制。实际执行批次必须回传，才能形成可信的溯源记录。

### 双方需确认

- 效期约束按出库时间还是预计到货时间判断。
- 批次替换、短拣、拆批及例外审批规则。
- 不满足约束时返回异常，不能静默放宽要求。

## 15. 客户 WMS 是否管理收货质检？

### 建议

已确认 WMS 包含质检：由 WMS 管收货、质检及最终放行，FoodOS 管采购和商务处理。

- FoodOS：采购单、供应商、约定数量价格、退货和结算依据。
- WMS：实收数量、批次效期、温度记录、质检结果、隔离及放行。
- 只有已放行数量才能进入可售范围。

FoodOS 接收并展示质检结果，不对同一批库存再次作放行决定；待检或隔离库存不得进入可售范围。

### 理由

收货、质检、上架和库存可用性紧密关联，分散决策容易造成未检先售或冻结失效。仅同步质检备注不能形成有效控制。

### 双方需确认

- 质检判定、复检、部分合格及退供应商流程。
- 哪个系统有最终放行权，另一个系统如何执行该结果。
- 实收、合格、可结算数量之间的关系。

## 16. 哪个系统创建发运单、路线和装车任务？

### 建议

拆分仓库执行与运输计划职责，不将不同含义的单据强行合并。

- FoodOS 创建客户交付需求：送给谁、送什么、何时送达。
- WMS 创建仓库出库执行单：拣货、复核、集货和实际出库。
- TMS 或 FoodOS 配送模块管理车辆、司机、路线和配送趟次。
- 配送侧提供车次与装载要求，WMS 负责扫描装车并回传实际装载结果。

已确认没有独立 TMS，由 FoodOS 承担配送计划和执行。

### 理由

客户订单、仓库执行单和运输单据可能拆分或合并，并非一对一关系。明确各自职责比要求所有系统共用一张发运单更容易维护。

### 双方需确认

- “发运单”在各系统中的具体含义及对应关系。
- 拆单、合单、分批配送、改车及漏装处理。
- 装车完成、仓库出库、车辆发车分别由哪个系统确认。

## 17. 签收来自司机端、客户 WMS，还是第三方 TMS？

### 建议

由实际承担配送执行的系统提供主签收记录，每个配送任务明确唯一来源。

- 本项目使用 FoodOS 配送能力采集签收及凭证，不另行对接第三方 TMS。
- WMS 仅负责仓储时，其出库完成不能视为客户签收。

区分配送签收与门店验收：前者表示交货完成，后者表示饭店确认数量、质量及差异。

### 理由

司机点击送达不等于门店认可全部商品。拒收、少货、破损和部分签收必须能表达，否则影响售后和结算。

### 双方需确认

- 主签收来源、签收凭证及授权人员。
- 部分签收、拒收、签收更正和门店异议处理。
- 哪个状态触发结算，哪些差异需要人工确认。

## 18. 客户 WMS 是否支持事件推送；如果不支持，增量查询机制是什么？

### 建议

事件推送优先，增量查询补偿，定期对账兜底。有推送也需要查询接口，以便失败补拉和状态核对。

只能轮询时，优先使用不透明增量游标或稳定递增的变更序号。如果只能按更新时间查询，应使用更新时间加唯一 ID 稳定分页、适当重叠查询窗口，并由接收端去重。取消、删除等变化也必须可查询。

### 理由

推送可能丢失、重复或乱序；仅查询更新时间大于上次时间，也可能漏掉同一时间点的数据。目标是允许重复、能够补偿、不漏处理，而非依赖消息只发一次。

### 双方需确认

- 事件范围、重试策略、鉴权方式、限流和可接受延迟。
- 游标语义、有效期、分页一致性及历史补拉范围。
- 查询失败后断点恢复和全量重建机制。

## 19. 是否存在多仓、多货主、多温区、多单位和拆零？

### 建议

要求客户提供真实业务样例，并明确一期支持范围，不能仅确认是否支持。

- 多仓：订单是否拆仓履约，仓间调拨由谁负责。
- 多货主：货物所有权，以及代管、寄售等业务。
- 多温区：商品、库位和车辆分别有哪些约束。
- 多单位：箱、包、件、公斤的换算关系是否固定。
- 拆零及称重：是否允许散件、半箱，以及是否按实际重量结算。

饭店租户不自动等于库存货主。饭店通常是采购客户，销售交付前的库存可能属于运营方，不能直接为每个饭店建立一个货主。

### 理由

这些维度影响库存识别、数量精度、履约拆分和对账，后补成本高；但不应为未确认的业务提前实现全部复杂能力。

### 双方需确认

- 一期实际使用的维度和限制。
- 基础计量单位、换算精度、舍入及称重差异规则。
- 货主与运营方、饭店租户之间的真实关系。

## 20. 是否有稳定的事件 ID、对象版本号或更新时间游标？

### 建议

尽量同时具备以下标识，它们用途不同，不能互相替代。

- 事件 ID：识别重复投递。
- 业务对象 ID 和版本号：识别旧状态，防止乱序覆盖。
- 增量游标：断点续传及补拉。
- 来源系统、发生时间和关联单据 ID：支持追踪和排障。

无法提供稳定版本号时，不应只按时间戳覆盖状态；需要合法状态转换校验，必要时查询源系统当前状态。

### 理由

去重不能解决乱序，版本号也不能找回从未收到的消息。三类能力共同支撑可靠同步。

### 双方需确认

- ID 唯一范围及重试时是否保持不变。
- 版本号是否按对象递增，以及更正、撤销是否增加版本。
- 时间戳精度、时区及游标保留期限。

## 21. 历史库存如何建立期初，并如何完成首次对账？

### 建议

采用统一基准时点快照、后续增量和分维度对账的切换方式。

1. 完成商品、仓库、货主和单位等基础资料映射。
2. 确定基准时点及对应事件序号或查询游标。
3. 导入该时点库存快照，覆盖可用、冻结、待检、已分配等必要状态。
4. 接续处理基准时点之后的变化，避免与快照重复计算。
5. 按仓库、商品、批次、货主和库存状态核对。
6. 差异处理完成并由双方确认后，再开放正式接单。

同时处理未收采购、待拣订单、已拣未发、已发未签、退货在途等未完成单据。

### 理由

只导库存、不处理在途单据，会导致重复扣减或漏加库存。必须先明确唯一权威来源，差异需要追查原因，不能让两套系统互相覆盖直到数字一致。

### 双方需确认

- 能否提供与游标一致的库存快照；不能时是否需要停作业切换窗口。
- 未完成单据的迁移或原系统闭环策略。
- 首次对账标准、差异审批人、切换失败回退方案。

## 三、对 FoodOS 的总体落地方向

保留已有自执行代码，但本项目仅实施外部 WMS 仓内执行，FoodOS 承担交易、客户服务和配送。对接仓库禁用 FoodOS 自执行，不新增双模式切换平台。

维护边界建议：

- 核心订单和客户服务流程不直接依赖客户 WMS 的私有字段及状态。
- 外部差异集中在对接边界进行映射，不把客户专属判断散落到核心业务。
- 外部仓库不得同时触发 FoodOS 自有批次分配、组波和拣货执行。
- 对接失败、重复、乱序、补拉及对账作为正常流程设计，而非上线后人工补救。
- 执行模式切换属于受控操作，需要处理存量任务，不能作为普通配置随意切换。
- 仅实现已确认的一期场景，不为未知 WMS 提前建设复杂通用平台。

## 四、双方评审完成条件

以上建议经双方逐条确认后，至少应形成以下成果，再进入接口设计与实施：

1. 库存、分配、波次、质检、出库、运输和签收的唯一责任方清单。
2. 单据及状态映射、库存口径、单位和货主规则。
3. 接口样例与事件样例，以及去重、乱序、补拉约定。
4. 一期业务范围和明确不支持的场景。
5. 期初切换、首次对账、异常处理和回退验收方案。

本次同步已确认业务决策及配套文档，不改变业务代码、运行配置或数据库；实现和联调状态仍按实施清单验收，不因决策确认自动勾选完成。
