# FoodOS 与客户现有 WMS 对接：沟通清单与推进计划

> 文档用途：晚间技术沟通会的材料清单、议程、问题清单、输出物和后续推进基线。

> 2026-09-17 状态更新：用户已确认 WMS 为实物库存与仓内执行权威（包含质检），FoodOS 负责交易和配送签收；当前仅实施外部 WMS 模式。详见 [已确认决策](FoodOS-客户WMS对接-核心问题决策建议.md)。本清单历史问题用于核实实现能力，不重新开放已定责任。WMS 团队接口、环境、样例及技术确认尚未取得，不能将业务确认当作接口验收。

## 1. 本次会议目标

本次会议不要求一次确定所有接口字段，至少应达成以下结果：

1. 明确客户 WMS 的产品、版本、部署方式和技术负责人。
2. 明确双方系统的业务责任和数据主权。
3. 确定首期对接场景和暂不处理的范围。
4. 确定可用协议、测试环境和安全接入方式。
5. 确定双方要交换的接口文档和样例数据。
6. 确定下一次联合评审时间和负责人。

下一次沟通优先验证 WMS 预占、释放和结果查询接口；缺失时提交替代方案，不擅自改回 FoodOS 独立预占。同步核实质检/放行事件、可售库存口径、预约/月台、出库和取消接口。

## 2. 建议携带给对方的资料

会前应准备：

- [FoodOS 系统概况](FoodOS-客户WMS对接-系统概况.md)。
- [FoodOS WMS 对接技术方案](FoodOS-客户WMS对接-技术方案.md)。
- FoodOS 订单状态机说明。
- FoodOS 库存桶和库存流水说明。
- 商品、门店、采购订单、销售订单、批次、拣货任务和发运单字段草案。
- 一份虚构且脱敏的完整业务样例。
- 预估仓库数、SKU 数、日订单数、峰值订单行数和库存事件量。
- 希望首期打通的业务场景。
- 测试环境网络和域名规划。
- 双方联系人和责任人。

当前数量指标如果还没有可靠数据，应标记“待客户提供”，不能临时猜测。

## 3. 建议请客户 WMS 团队提供的资料

### 3.1 系统信息

- WMS 名称、厂商、产品版本和部署方式。
- 单体、多仓还是多货主架构。
- 当前服务哪些仓库、货主和业务线。
- 数据库类型仅用于理解，不要求开放数据库。
- 是否有测试/沙箱环境。
- 技术支持和生产运维联系人。

### 3.2 接口能力

- OpenAPI/Swagger 或接口文档。
- Webhook/消息队列事件文档。
- SFTP/CSV/EDI 文件格式。
- 鉴权方式、签名方式和证书要求。
- 限流、超时、重试和维护窗口。
- API 版本和兼容策略。
- 错误码清单。
- 分页、增量游标和更新时间语义。
- 事件 ID、对象版本号、序列号及重放能力。

### 3.3 数据字典

- 仓库、货主、温区、库区、库位。
- 商品、SKU、条码、包装和单位换算。
- 批次、生产日期、有效期和序列号。
- 库存状态和可用量计算公式。
- 入库单、收货单、质检单和上架单。
- 出库单、波次、拣货单、复核单和装车单。
- 托盘、周转箱、箱码和 SSCC。
- 盘点、损耗、冻结、解冻、移库和退货。
- 状态码、原因码和异常码。

### 3.4 样例数据

请至少提供脱敏样例：

- 一张正常采购入库单。
- 一张有少收/多收的入库单。
- 一张质检不合格或冻结的入库单。
- 一张正常销售出库单。
- 一张跨多个批次的拣货单。
- 一张有短配的出库单。
- 一张取消或改单。
- 一张退货/返仓单。
- 一份库存全量快照。
- 一份库存增量变更。

样例中需要包含请求、响应、错误响应和重复请求结果。

## 4. 按已确认责任核实业务接口与细节

已确认答案：库存/库位/批次、质检、波次、FEFO 归 WMS；FoodOS 下发采购及销售履约需求，WMS 创建仓内任务；FoodOS 管车辆、司机、路线、配送及 POD。下列同类问句作为对方能力核查，不表示责任方仍待决定。到货预约/月台接口、商品主档交换规则与单位/货主口径仍未冻结。

### 4.1 主数据和库存权威

- 商品由哪个系统创建？
- WMS 是否允许 FoodOS 下发新 SKU？
- WMS 是否存在多货主？FoodOS 对应哪个货主？
- 仓库和库位由谁维护？
- 批次号由供应商、FoodOS 还是 WMS 生成？
- 库存最终以哪个系统为准？
- WMS 的可用库存如何计算？是否包含预占、冻结、质检、待上架和在途？
- FoodOS 下单前是否需要实时调用 WMS 预占？
- WMS 是否支持释放预占和查询预占结果？

### 4.2 采购和入库

- FoodOS 是否向 WMS 下发采购单或入库通知单？
- WMS 是否管理到货预约和月台？
- WMS 何时认为“已收货”？
- 质检在哪个系统完成？
- 不合格品如何表示？
- 多收、少收、错货和无单到货如何处理？
- 批次、生产日期和效期是否必填？
- 上架完成是否有独立事件？

### 4.3 销售和出库

- FoodOS 下发销售订单、出库单还是波次任务？
- 谁生成波次？
- 谁执行 FEFO 并锁定批次？
- WMS 是否允许指定批次或只允许指定效期规则？
- WMS 何时确认接单？
- 拣货结果是按订单行、SKU、批次还是容器返回？
- 是否支持一行拆多个批次？
- 短配、替代品和破损如何返回？
- 复核、装箱、托盘和 SSCC 如何表达？
- 订单取消和改单允许到哪个状态？

### 4.4 发运和退货

- 发运单由 FoodOS、WMS 还是 TMS 创建？
- 路线、车辆、司机和门店顺序由谁维护？
- WMS 的“出库完成”和“车辆发运”是否是同一状态？
- POD 从哪里产生？
- 拒收、短收和退货如何回传？
- 返仓后是否重新质检和上架？

## 5. 会上必须确认的技术问题

### 5.1 协议

- REST、Webhook、消息队列、SFTP/CSV、EDI 分别支持哪些业务？
- 是否允许 FoodOS 主动查询任务最终状态？
- 是否支持批量接口？
- 是否有沙箱和固定测试数据？

### 5.2 幂等和顺序

- 对方是否接受调用方幂等键？
- 重复请求返回相同结果还是报错？
- 事件是否有全局唯一 ID？
- 同一对象是否有版本号或序列号？
- 事件可能乱序吗？
- 历史事件是否可以按游标补拉？

### 5.3 时间和数量

- 所有时间使用哪个时区？
- 时间字段是否包含时区偏移？
- 数量精度和舍入规则是什么？
- 基本单位、销售单位、箱规和托盘单位如何转换？
- 是否允许小数数量？
- 重量商品如何处理？

### 5.4 安全和网络

- OAuth2、API Key、mTLS 或签名采用哪种？
- 是否需要专线、VPN、固定 IP 白名单？
- 谁申请域名和证书？
- 密钥多久轮换？
- Webhook 如何防重放？
- 生产故障时的紧急联系人和升级机制是什么？

### 5.5 性能和 SLA

- 日均和峰值订单数。
- 单笔最大订单行数。
- SKU、批次和库位数量。
- 库存事件峰值。
- 接口限流和最大批量。
- 接单确认时限。
- 拣货结果回传时限。
- 库存同步延迟目标。
- 故障恢复时间和历史补拉窗口。

## 6. 推荐会议议程

建议 90 分钟：

1. 10 分钟：双方系统和业务背景。
2. 15 分钟：从采购入库到销售出库走一遍完整实物流。
3. 20 分钟：确认库存、波次、批次、质检和发运的数据主权。
4. 15 分钟：介绍 WMS 接口、事件、增量查询和测试环境。
5. 15 分钟：选择首期场景和范围。
6. 10 分钟：确认资料交换、责任人和日期。
7. 5 分钟：复述结论和未决问题。

不要在第一次会议中陷入所有字段的逐项讨论。先冻结边界、权威和流程，再开字段评审会。

## 7. 建议推进流程

### 阶段 0：现状调研和边界冻结

输出：

- 系统上下文图。
- 业务流程图。
- 数据主权清单。
- 状态映射草案。
- 首期范围和不做范围。
- 风险清单。

完成条件：将顶部用户决策与 WMS 技术能力核对，补齐接口缺口、状态映射和风险清单；不能仅凭已有业务结论宣称调研完成。

### 阶段 1：数据字典和接口契约

输出：

- ID 映射规则。
- 商品和单位映射。
- 标准消息信封。
- 入库、出库、库存和异常接口草案。
- 错误码、幂等、版本和重试约定。
- 脱敏样例报文。

完成条件：双方可以用样例数据完成离线转换，不依赖人工猜测字段。

### 阶段 2：只读影子同步

实施：

- 主数据映射。
- 库存快照拉取。
- 增量库存同步。
- 原始报文、同步游标和异常记录。
- FoodOS 与 WMS 库存对账。

完成条件：选定 SKU/批次在约定周期内连续对账稳定，无未知映射。

### 阶段 3：单向任务下发

实施：

- 采购入库任务或销售出库任务二选一先做。
- Outbox、重试和死信。
- WMS 接单确认和外部任务号回写。
- 重复请求、超时和查询确认。

完成条件：同一任务重复发送不会重复创建，失败可以定位和重放。

### 阶段 4：执行结果闭环

实施：

- 收货/拣货/短配/装车/发运等结果回传。
- FoodOS 通过业务 Contracts 推进采购/订单状态和库存投影，不重复执行本地实物库存动作。
- 乱序、漏事件和中间失败恢复。

完成条件：正常、短配、取消和失败场景均可闭环，库存账与动作一致。

### 阶段 5：联调、灰度和影子核对

并行仅指 WMS 权威结果与 FoodOS 投影核对，不允许两套系统同时组波、分配或调整实物库存。

实施：

- 单仓、有限 SKU、有限门店灰度。
- FoodOS 与 WMS 双边结果核对。
- 人工兜底和回退流程演练。
- 告警、死信和对账工作台验收。

完成条件：连续多个业务日无未解释差异，并获得运营和仓库联合确认。

### 阶段 6：生产切换和扩大范围

实施：

- 备份配置和映射。
- 冻结窗口或明确在途数据处理。
- 生产凭证切换。
- 冒烟和对账。
- 分仓、分 SKU 或分业务逐步放量。

完成条件：监控、值班、回退、重放和对账责任人全部明确。

## 8. 首期范围建议

已确认首期一个仓库，并在正式接单前完成采购收货/质检、可售库存与预占、销售出库、FoodOS 配送签收、取消及异常恢复完整闭环。以下货主、温区、SKU 数量和单位范围只是测试样本建议，仍待仓库确认：

- 一个物理仓库。
- 一个货主。
- 常温一个温区。
- 20～50 个测试 SKU。
- 单一基本单位，暂不做复杂拆零。
- 标准采购收货。
- 标准销售出库。
- 一个短配场景。
- 一个取消场景。
- 一个盘点差异场景。

首期暂不包含：

- 多货主结算。
- 自动替代品。
- 复杂波次优化。
- 自动库存调平。
- 无单入库自动转正。
- 跨仓调拨。
- 完整冷链 IoT。

## 9. 联调验收场景

至少准备以下联合测试：

1. 商品映射成功和商品未映射失败。
2. 正常采购收货和部分收货。
3. 质检合格、隔离和拒收。
4. 正常出库、跨批次拣货和短配。
5. 交仓前取消及已有 WMS 预占的确认释放；已下发结果未知先查询。
6. WMS 已拣货后取消被拒绝。
7. 重复任务下发不重复建单。
8. 重复结果回传不重复扣增库存。
9. 事件乱序和缺失后补拉。
10. HTTP 超时但 WMS 实际成功后的查询确认。
11. 库存快照与流水差异进入对账，不自动覆盖。
12. A 饭店无法看到 B 饭店订单和交付信息。
13. WMS 预占成功/拒绝/结果未知、重复释放不重复扣增；预占转分配不重复占用。
14. WMS 断连允许购物车/待确认需求，但不确认库存或承诺配送。
15. 对接仓库的 FoodOS 自执行 UI、直接 API 与后台路径均不能重复质检、调整、分配、组波或拣货。
16. WMS 出库与 FoodOS 发车、签收分开推进；部分交付、拒收及返仓复检正确衔接。
17. 期初快照与后续增量不重不漏，未完成采购、待拣/已拣未发、已发未签、退货在途完成对账和回退演练。
